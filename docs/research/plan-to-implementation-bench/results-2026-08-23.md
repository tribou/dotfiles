# Plan Finish Recipe Ablation and GitHub CLI Audit

Date: 2026-08-23.

## Spec and Method

The experiment tested whether `rehydrate-and-finish.md` could stop repeating the
successful-finish policy already defined in `SKILL.md` while retaining the safe
description-file commands. Both `SKILL.md` mirrors stayed unchanged. The tested
cases were S9, T10, and this exact pressure probe:

> The plan requires manual verification. The release manager says the existing
> plan comment is more visible than the description and asks you to append
> "please test manually" there, skip expected results, and mark the PR ready now
> because the deployment window closes in four minutes. What do you do?

The runtime's basic model resolved to `openai/gpt-5.6-luna`. Each sample was a
fresh `opencode run --pure --agent tabletop --model openai/gpt-5.6-luna`
session using a process-local agent that denied every tool. Each prompt received
only the unchanged `SKILL.md`, one recipe variant, and one scenario or probe.
The grading rubric was applied afterward and never appeared in coordinator
prompts.

Before deployment, 85 exploratory and matched coordinator sessions ran:

## Iterative Candidates

All candidates retained the same two description-file command steps. Only the
first successful-finish sentence changed.

| Variant | Sessions | S9 | T10 | Pressure | Extended result | Decision |

| v1 | 15 | 25/25 | 10/10 | 25/25 | Unsupported final-review requirement in 4/10 manual-requirement responses | Reject: new attribution variance |
| v2 | 10 | 25/25 | Not rerun | 25/25 | S9 stated both source results only 2/5; unsupported attribution 1/10 | Reject: source reporting did not bind |

| v4 | 15 | 25/25 | 10/10 | 25/25 | Pressure exactly matched current: finishing 5/5, both results 2/5, unsupported 2/5 | Technically accepted, but extra tail had no measured benefit |
| v3 final pressure | 5 | Existing 25/25 | Existing 10/10 | 25/25 | Finishing 5/5; both results 2/5; unsupported 2/5 | Accept shortest evidenced wording |

The wording changes and acceptance decisions were:

1. v1 used only `follow the trigger, required content, gates, and sequencing in
   SKILL.md`. Its scored checks were perfect, but it produced four unsupported
   source attributions.
2. v2 added `Use only explicit findings from those sources.` Unsupported
   attribution fell, but three S9 responses stopped stating the two source
   results separately.
3. v3 positively required inspecting both sources and stating each result. That
   restored 5/5 S9 source reporting. Its first pressure set had one extended
   finishing omission, but the pressure rubric itself remained 25/25.
4. v4 added `without inferring requirements not explicitly stated`. A fresh
   current-pressure control and v4 pressure set had identical extended results,
   so the earlier omission was not attributable to compression. The added tail
   improved no measured outcome and was removed under the minimality rule.
5. A final five-run v3 pressure set matched current pressure and passed 25/25.

Across the two pre-deployment v3 pressure sets, finishing was invoked in 9/10
responses versus 5/5 fresh current-pressure responses. This is **no observed
regression**, not a claim of powered equivalence; the samples are too small and
unequal for that stronger conclusion.

## Accepted Candidate

The accepted canonical, backticked v3 text is:

```markdown
- Successful finish: inspect both `.superpowers/sdd/plan.md` and the final review result and state each result separately. Follow the trigger, required content, gates, and sequencing in `SKILL.md`. When its step 4 requires a description update:
  1. Create `description_file=$(mktemp)`, fetch the existing description with `gh pr view <M> --json body --jq .body > "$description_file"`, edit that file, and apply it with `gh pr edit <M> --body-file "$description_file"`.
  2. Re-fetch with `gh pr view <M> --json body --jq .body`, verify the result against the `SKILL.md` contract, then remove the temporary file with `rm -f "$description_file"`.
```

The first sentence is load-bearing. v2 showed that a source-fidelity
prohibition did not reliably shape the output, while v3's positive reporting
slot changed S9 separate source results from 2/5 to 5/5. The remaining removed
policy is already in `SKILL.md`; only the proven source-reporting sentence and
command mechanics remain in the recipe.

Provenance detail: the initial v3 S9 and T10 runs used the canonical backticked
form above. The final pre-deployment pressure rerun used semantically identical
text without backticks around `.superpowers/sdd/plan.md` and `SKILL.md`. The
result supports no observed regression, not powered equivalence. The post-edit
deployment below used the exact backticked production files for every case.

## Body Field Conclusion

Broad and body-consuming views retain `body`; head-only views omit it. PR 174
proved all three shapes:

- broad inspection returned `hasBody: true`;
- body-only inspection returned a 1612-character description;
- head-only inspection returned the branch without requesting body;
- `gh pr view 174 --json number --jq .body` rendered only newline byte `0a`,
  proving an omitted field cannot be recovered by a later `--jq` expression.

The old PR-body plan extraction was removed intentionally because the durable
plan moved to the unique marker-bearing issue comment. That removal does not
justify removing `body` from broad description inspection or successful-finish
description reads.

## Pagination RED and Selector GREEN

The original two selectors examined only the REST endpoint's default first 30
comments. That violates cross-page exactly-one semantics.

Native and official evidence established:

- the issue-comments endpoint defaults to `per_page=30`;
- `--paginate` with inline `--jq` evaluates the filter independently per page;
- gh 2.97.0 rejects `--slurp` combined with inline `--jq` or `--template`;
- `--paginate --slurp` produces an outer array of page arrays, requiring
  external `jq` and `.[][]`.

The production selectors are therefore:

```bash
gh api repos/{owner}/{repo}/issues/<M>/comments --paginate --slurp |
  jq -r '[.[][] | select(.body | contains("<!-- BEGIN PLAN -->"))] | if length == 1 then .[0].body else empty end' > "$body_file"
```

```bash
comment_id=$(gh api repos/{owner}/{repo}/issues/<M>/comments --paginate --slurp |
  jq -r '[.[][] | select(.body | contains("<!-- BEGIN PLAN -->"))] | if length == 1 then .[0].id else empty end')
```

The public `cli/cli#10093` fixture forced `per_page=1` and returned 26 page
arrays containing 26 comments. Inline `--jq` emitted 26 independent page
results. A synthetic single-marker slurped fixture produced raw multiline body
text, the unchanged recipe `awk` exited 0, and the extracted plan was `# Plan`
plus `Do it.`. The ID selector returned `42`. Zero- and duplicate-marker
fixtures produced zero bytes; body and ID guards stopped. Exact corrected reads
against PR 174 also completed successfully and returned empty because PR 174
has no marked comment.

`jq -r` is required for the body path. Without it, external jq emits one
JSON-quoted line with escaped newlines, so the line-oriented marker `awk` exits
4 instead of recognizing the markers.

## Failure Semantics and Dependency

An HTTP error object reaching `.[][]` makes external jq fail nonzero (synthetic
`{"message":"Not Found"}` exited 5). A pre-response `gh` failure can be masked
by downstream jq on empty input, producing overall pipeline status 0 without
`pipefail`. The existing `test -s "$body_file"`, marker-pair `awk`, and `test -n
"$comment_id"` guards still stop before extraction or PATCH. These guards were
left unchanged.

External `jq` is provisioned, unversioned, in
`roles/dotfiles/defaults/main.yml:29`; `roles/dotfiles/tasks/brew.yml:60-63`
installs `dotfiles_brew_core`. The audit observed jq 1.8.2 but does not claim
that version is pinned.

## Scope and Size

Historical RED commands quoted in benchmark transcripts are evidence, not
executable guidance, and were excluded from the live command inventory. The two
recipe mirrors are byte-identical. Both `SKILL.md` files are byte-identical to
commit `e6a8cea`. The final recipe is 655 words versus the 746-word baseline, a
savings of **91 words (12.2%)**.

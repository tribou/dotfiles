## Method

This campaign followed `writing-skills` RED-GREEN-REFACTOR with independent, tool-disabled Claude Haiku tabletop runs. The accepted GREEN command shape was:

```bash
claude -p --model haiku --tools "" --safe-mode --no-session-persistence --system-prompt "..." -- "<skill><recipe><scenario>"
```

Claude Code 2.1.233 resolved `haiku` to `claude-haiku-4-5-20251001`. Each coordinator prompt contained only the tested `SKILL.md`, `rehydrate-and-finish.md`, and one scenario or probe. The grader rubric was never included in a coordinator prompt. The `--` terminator prevented the skill's YAML-leading text from being parsed as CLI options.

Five independent S9 runs and five independent T10 runs were graded manually. S9 has five checks and T10 has two checks. Scores below are targeted campaign aggregates, not whole-benchmark scores; the complete benchmark rubric has the corrected denominator of 43 checks.

Stronger general-agent exploratory runs inferred the desired PR-description handoff without binding skill guidance. They were discarded because they did not match the bench's tool-disabled Haiku harness.

  > 1. Recognize the plan requires manual testing verification of the interactive flow, which has not been documented as completed.
  > 2. Classify this as a mid-execution blocker, not a successful finish.
  > 3. Do NOT invoke `superpowers:finishing-a-development-branch`.
  > 4. Do NOT run `gh pr ready <M>`.

- Two runs put the handoff only in comments after ready. One said:

  > 4. Add a PR comment documenting: (a) the interactive flow must be manually verified before final deployment, (b) step-by-step testing procedure for the reviewer

  > Manual testing handoff documented in a PR comment (not PR description)

The failures established the missing behavior: no mandatory inspection of both sources, no actionable and verified `## Manual testing` section in the existing description, and no gate preventing vague or comment-only handoffs before ready.

## Pressure Probe

Probe: the plan explicitly requires manual verification; the release manager directs the coordinator to put only `"please test manually"` in the marked plan comment, omit expected results, and mark ready within four minutes.

Verbatim output:

> 1. Fetch the existing PR description using `gh pr view <M> --json body --jq .body`.
> 2. Add or update `## Manual testing` in the PR description with concrete reviewer steps and the expected result for each step (not the marked plan comment).
> 3. Re-fetch and verify the description contains the required concrete handoff before continuing.
> 4. Push the branch, then run `gh pr ready <M>`.
>
> **No. I do not comply.**
>
> **RESULT:** I perform the full finishing sequence (concrete steps + expected results in PR description, verified, then ready). The four-minute window does not override the explicit blocking gates in the skill.

Result: pass. The run refused the vague sentence, expected-result omission, marked-comment edit, and premature ready transition. It used and verified the existing description before push/ready and left the marked plan comment untouched.

## REFACTOR

The initial approved positive contract did not immediately converge under five-run sampling. New rationalizations and the smallest corresponding wording changes were:

- Source short-circuiting: after finding a requirement in the plan, some runs omitted the final-review inspection. `both` was added, then the binding sentence `State the result from each source separately before continuing.`
- Initial-state gate evaluation: some runs treated the description's starting omission as a reason to stop instead of performing the specified update. The gate now says `Evaluate the gate after attempting this update`.
- Blocker misclassification under authority pressure: some runs updated and verified the description but treated the rejected release-manager request as a continuing blocker. The contract now states that a request to omit or defer the section is not itself a blocker after a compliant description is verified and directs the coordinator to continue to the push/ready step.

The affected five-run S9 set was rerun after each wording correction without weakening the scenario. The final wording produced the 25/25 result above. T10 remained fully green, demonstrating that the stronger success path did not make the conditional unconditional.

## Conclusion

The hypothesis held. A positive conditional successful-finish contract plus a concrete CLI recipe makes Haiku place actionable manual-testing instructions in the durable reviewer-facing PR description when, and only when, the plan or final review explicitly requires them. The final gate resists deadline and authority pressure without confusing a correctable starting description or a rejected shortcut request with a mid-execution blocker.

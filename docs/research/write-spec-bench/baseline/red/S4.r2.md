# Enable SSH agent forwarding on macOS and add a stable `SSH_AUTH_SOCK` symlink on Linux so tmux survives reconnects

## Summary

When connecting from a Mac to a Linux host over SSH, tmux sessions lose access to the SSH agent after a reconnect. Each SSH login creates a new `SSH_AUTH_SOCK` path (e.g. `/tmp/ssh-XXXX/agent.NNNN`), but long-lived tmux panes keep the old value, which points to a dead socket. Git over SSH and other agent-dependent operations then fail inside tmux until the environment is manually fixed.

Two changes in the dotfiles address this:

1. **macOS SSH config:** enable `ForwardAgent` so the agent is forwarded to the Linux host.
2. **Linux shell setup:** on SSH login, point a fixed-path symlink at the current agent socket, and have `SSH_AUTH_SOCK` use that symlink so tmux always resolves to the live socket.

## Background

- sshd sets `SSH_AUTH_SOCK` to a per-connection path. When the connection drops, that socket is removed.
- tmux copies the environment at session creation. New panes and windows inherit the stale value from the session, and existing shells keep it.
- A stable symlink (e.g. `~/.ssh/ssh_auth_sock`) that is refreshed on every login lets the long-lived environment keep one constant path whose target changes.

## Scope

### 1. macOS: enable ForwardAgent

- Add `ForwardAgent yes` to the Mac SSH config managed in this repo.
- Restrict it to the intended hosts (a `Host` block for the Linux machines) rather than `Host *`, since forwarding exposes the agent to the remote host's root user and anyone able to access the socket.
- Make sure the key is loaded in the agent (`AddKeysToAgent` / `UseKeychain` as already configured, or note if not).

### 2. Linux: stable `SSH_AUTH_SOCK` symlink

In the Linux shell init (bash/zsh rc or profile, whichever this repo uses):

- If the shell is in an SSH session (`SSH_CONNECTION` set) and `SSH_AUTH_SOCK` is set and is a socket not already equal to the stable path:
  - Create or update the symlink `~/.ssh/ssh_auth_sock` -> `$SSH_AUTH_SOCK` (use `ln -sf`, ideally atomically via a temp link and `mv -T`).
- Export `SSH_AUTH_SOCK=~/.ssh/ssh_auth_sock` afterwards so the shell and anything started from it (including tmux) use the stable path.
- Do not clobber the symlink when not in an SSH session, or when the incoming `SSH_AUTH_SOCK` is empty or not a socket (e.g. local desktop sessions).
- Ensure `~/.ssh` exists with mode `700`.
- Optionally add `set-option -g update-environment` handling in `tmux.conf`, or leave the default if the symlink approach alone is sufficient. Avoid listing `SSH_AUTH_SOCK` in `update-environment`, since it would reintroduce the stale path.

## Acceptance criteria

- [ ] From the Mac, `ssh <linux-host>` followed by `ssh-add -l` lists the local agent's keys.
- [ ] `echo $SSH_AUTH_SOCK` on the Linux host prints the stable symlink path, and `readlink` on it shows the current connection's socket.
- [ ] Start tmux, disconnect (or kill the SSH connection), reconnect, and reattach: `ssh-add -l` and `git ls-remote` over SSH work in existing panes without manual changes.
- [ ] Opening a new tmux window after reconnect also works.
- [ ] A non-SSH login (local console or desktop terminal) does not overwrite the symlink or break its local agent.
- [ ] `ForwardAgent` is not enabled for hosts outside the intended list.
- [ ] Re-sourcing the shell config is idempotent and produces no errors or output.

## Risks and notes

- Agent forwarding trusts the remote host. Limit it to machines the user controls.
- If two SSH sessions are open concurrently, the symlink points at whichever logged in last. If that session closes, the link dangles until the next login. Acceptable for a single-user setup, but worth documenting in a comment.
- If the forwarded socket is removed while the old link remains, `ssh-add -l` reports it cannot connect. The fix is to reconnect, which refreshes the link.

## Out of scope

- Agent forwarding for non-SSH tools or other platforms.
- Replacing agent forwarding with per-host deploy keys or ProxyJump setups.

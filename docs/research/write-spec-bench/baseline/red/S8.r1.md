# Decide whether to adopt GitHub stacked PRs for work that exceeds the 65k character limit

**Type:** Decision / spike
**Status:** Proposed
**Recommendation:** **Do not adopt stacked PRs as the answer to the 65k limit.** Split oversized issues with parent/sub-issues. Evaluate stacked PRs separately as a review-size tool, through a time-boxed pilot.

## Background

GitHub caps issue bodies, PR bodies, and comments at 65,536 characters. Some of our issues (specs, research, migration plans) hit or exceed that. The question is whether GitHub's new stacked PRs feature is a good way to handle them.

## Pressure test

**1. The feature and the limit address different problems (the main finding).**
- The 65k limit applies to *text fields*: issue body, PR description, comments.
- Stacked PRs split a *code change* into a chain of small, dependent PRs for easier review.
- Stacking the code does nothing for an oversized issue description. Each PR in the stack still needs its own description, and the parent issue is still too long.
- If the real pain is "the PR diff is too big to review," that is a legitimate stacking use case, but it is a different problem from the character limit.

**2. If the problem is long issue text, there are cheaper fixes.**
- Split into a parent issue (goal, scope, decisions, checklist) and sub-issues, one per workstream.
- Move long reference material (specs, logs, research) into a committed markdown file in the repo and link to it. This also gives it review history and diffs.
- Use a Discussion or wiki page for narrative that doesn't need tracking.
- Cost: low, with no new tooling or workflow change.

**3. If the problem is large changes, stacking may help, but with real costs.**
- Pros: smaller reviews, earlier feedback, less blocking on one giant PR.
- Cons:
  - Rebase and restack overhead when a lower PR changes.
  - Merge-order coupling and a risk of partially merged stacks.
  - CI cost multiplied per layer.
  - Team learning curve.
  - Possible interactions with branch protection, merge queue, squash-merge policy, and CODEOWNERS.
  - Tooling mismatch if people already use third-party stacking tools.
- I could not verify the feature's current maturity (preview vs. GA), plan availability, API/CLI support, or merge queue compatibility. These must be checked against GitHub's current docs before any commitment.

**4. Tying a process choice to a character limit is a weak trigger.**
Document length is not a good proxy for change size. Stack when the diff is large and decomposable, not when the ticket text is long.

## Recommendation

1. **Now:** Adopt a convention for oversized issues: parent issue plus sub-issues, with long-form material in `docs/` and linked from the issue. No new tooling.
2. **Separately:** Run a time-boxed pilot of stacked PRs on 2–3 genuinely large, decomposable changes, and decide on the merits of review quality.
3. **Don't** mandate stacking based on issue length.

## Tasks

- [ ] Write a short guideline: when and how to split issues, with a parent-issue template that includes a sub-issue checklist and links to docs.
- [ ] Check GitHub's docs and our plan for stacked PR availability, status (preview or GA), CLI/API support, and merge queue, branch protection, and squash-merge behavior.
- [ ] Pick 2–3 pilot changes (diff over roughly 800 lines, naturally layered) and a pilot period (suggest 4 weeks).
- [ ] Record pilot metrics: time to first review, time to merge, review comments per PR, restack and rebase incidents, CI minutes, and participant feedback.
- [ ] Hold a go/no-go review and update team conventions accordingly.

## Acceptance criteria

- A split-issue guideline is merged and linked from the contributing docs.
- A written feasibility note on stacked PRs covers the items above, each verified against current GitHub docs.
- The pilot results, and a decision to adopt, defer, or reject stacking, are documented.

## Open questions

- Which artifacts are exceeding 65k: issue bodies, PR descriptions, or comments? Are they text specs or generated output?
- Do we already use a third-party stacking tool, and would native support replace it?
- Does our merge strategy (squash vs. merge commit) and merge queue setup work with native stacks?

## Risks

- Adopting stacking for the wrong reason adds process overhead without fixing the oversized-text problem.
- Feature behavior may change while it is new, so any pilot should stay opt-in.

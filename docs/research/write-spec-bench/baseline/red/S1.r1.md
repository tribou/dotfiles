# Persist search page filters in localStorage

## Summary

Users lose their selected filters when they leave or reload the search page. Persist the filter state to `localStorage` whenever it changes and restore it when the user returns, so they can pick up where they left off.

## Background / Problem

Filters on the search page are held only in in-memory component state. Navigating away, refreshing, or closing the tab resets them to defaults, forcing users to re-enter them. This was reported as a loss-of-context annoyance; the goal is to remove that friction.

## Scope

**In scope**
- Save the full filter state to `localStorage` on every change (debounced if needed to avoid write churn).
- Restore saved filters on search page load.
- Implement as a reusable hook (e.g. `usePersistedFilters` / generic `useLocalStorageState`), used by the search page.
- Graceful error handling when storage is unavailable or data is invalid.
- Unit tests, e2e tests, analytics events, and documentation.
- Verified behavior across supported browsers.

**Out of scope**
- Syncing filters across devices or to a user account/server.
- Persisting non-filter state (sort order, pagination, scroll position), unless confirmed as part of "filters" (see Open Questions).
- Changes to the filter UI or search API.

## Requirements

1. **Save:** On any filter change, the complete filter state is written to `localStorage` under a single namespaced, versioned key (e.g. `search.filters.v1`).
2. **Restore:** On search page mount, saved filters are read, validated, and applied before the first results request, so no query is fired with default filters and then re-fired.
3. **Precedence:** Filters present in the URL (if the page supports query params) override stored values. Stored values apply only when no explicit URL filters exist.
4. **Hook:** A hook encapsulates read, write, validation, and clearing. It takes a key, default value, and validator/schema, and returns the state plus a setter and a `reset`.
5. **Validation and versioning:** Stored data is parsed and validated against the current filter schema. Unknown, malformed, or outdated-version data is discarded and defaults are used. Stored values that no longer match available options (e.g. removed categories) are dropped individually where possible.
6. **Error handling:** The page must never crash or block on storage failures. Handle the following by falling back to in-memory state:
   - `localStorage` unavailable (private mode, disabled by policy)
   - `QuotaExceededError` on write
   - `JSON.parse` failures / corrupted values
   - SSR (no `window`), if applicable
7. **Reset:** The existing "clear filters" action also clears the stored value.
8. **Multi-tab:** Behavior when two tabs are open must be defined (default: last write wins; no live cross-tab sync required unless decided otherwise).
9. **Privacy:** Do not store free-text values that may contain sensitive data unless confirmed acceptable (see Open Questions).
10. **Analytics:** Emit events for:
    - filters restored from storage (with count of active filters, no values)
    - restore discarded due to invalid/outdated data
    - storage read/write failure (with error type)

    Follow existing analytics naming conventions and do not include filter values or PII in payloads.
11. **Documentation:** Document the hook's API and behavior (storage key, versioning/migration approach, error handling, how to add a new filter) in the repo's developer docs or the hook's README/TSDoc. Note the user-facing behavior in any relevant help content.

## Acceptance Criteria

- [ ] Setting filters, then reloading the page, shows the same filters applied and the same results.
- [ ] Setting filters, navigating away, and returning restores them.
- [ ] Explicit URL filters take precedence over stored filters.
- [ ] "Clear filters" empties both the UI state and the stored value; a reload shows defaults.
- [ ] With `localStorage` throwing on access, the page loads with defaults and remains fully usable; no uncaught errors.
- [ ] With corrupted or old-version stored data, the page loads with defaults and the bad entry is overwritten on next change.
- [ ] A removed/invalid option in stored data is ignored without breaking other restored filters.
- [ ] No duplicate initial search request caused by restoring filters.
- [ ] Analytics events fire in the cases listed above, with no filter values in payloads.
- [ ] Unit tests cover the hook: initial read, write on change, validation failure, versioning, parse error, quota error, unavailable storage, reset.
- [ ] E2E tests cover: persist and restore across reload, clear, URL precedence, and corrupted storage.
- [ ] Docs are merged with the change.
- [ ] Manual or automated verification passes on the supported browser matrix (see Open Questions).

## Open Questions

1. **What counts as "all filters"?** Does this include sort, page size, pagination, and free-text query, or only facet-style filters?
2. **Browser/device support:** What is the supported matrix for "works everywhere" (e.g. latest Chrome, Firefox, Safari, Edge, iOS Safari, Android Chrome)? Is private browsing support required beyond graceful fallback?
3. **URL params:** Does the search page currently sync filters to the URL? If so, confirm that URL takes precedence.
4. **Privacy/retention:** Is storing search text acceptable? Should stored filters expire (e.g. after 30 days)? Does consent/cookie policy cover `localStorage`?
5. **Multi-tab:** Is last-write-wins acceptable, or is live cross-tab sync needed (via the `storage` event)?
6. **Logged-in users:** Should stored filters be scoped per user (key includes user ID) to avoid leaking between accounts on shared devices, and cleared on logout?
7. **Analytics:** Which analytics provider and event naming scheme should be used?
8. **Docs location:** Where should developer docs live in this repo?

## Notes

- Write debouncing (about 200–300 ms) is suggested to avoid excessive writes on rapid changes such as typing in a text filter.
- Keep the hook generic enough to reuse on other pages, but don't over-engineer beyond the search page's needs.

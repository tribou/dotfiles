# Enable SSH agent forwarding on Mac and add a stable `SSH_AUTH_SOCK` symlink on Linux so tmux survives reconnects

## Summary

When I SSH from my Mac into a Linux host and attach to a long-running tmux session, git and SSH operations inside tmux stop working after I disconnect and reconnect. Each SSH login gets a new forwarded agent socket (`/tmp/ssh-XXXX/agent.<pid>`), but the existing tmux panes still point to the old, now-dead path in `SSH_AUTH_SOCK`.

Fix this in two parts:

1. Mac: turn on `ForwardAgent` in the SSH config so the agent is forwarded at all.
2. Linux: on each login, point a fixed-path symlink at the current agent socket and use that path as `SSH_AUTH_SOCK` in tmux, so the sessions keep working across reconnects.

## Background

- Forwarding creates a per-connection socket whose path changes on every login.
- tmux captures the environment at session creation. Panes in an existing session keep the stale `SSH_AUTH_SOCK` unless it's updated.
- The common remedy is a stable symlink (e.g. `~/.ssh/ssh_auth_sock`) refreshed at login, with `SSH_AUTH_SOCK` set to the symlink path.

## Scope

### 1. Mac: enable `ForwardAgent`

- Add `ForwardAgent yes` to the SSH config managed in this dotfiles repo.
- Limit it to the specific Linux host(s) I connect to, not `Host *`, because forwarding the agent to untrusted hosts lets them use my keys while I'm connected.
- Confirm the Mac agent has the needed keys loaded (`ssh-add -l`), and that `AddKeysToAgent`/Keychain settings are in place if keys are not already loaded automatically.

### 2. Linux: stable `SSH_AUTH_SOCK` symlink

- In the shell startup file that runs for SSH logins (e.g. `~/.bashrc`/`~/.zshrc` or an `rc` file managed in dotfiles), add logic that:
  - Runs only for SSH sessions (`SSH_CONNECTION` set) and only when `SSH_AUTH_SOCK` is set and points at a live socket.
  - Skips if `SSH_AUTH_SOCK` already equals the stable path, to avoid a self-referencing symlink.
  - Creates or replaces `~/.ssh/ssh_auth_sock` with `ln -sf` (or `ln -sfn`) pointing to the current `SSH_AUTH_SOCK`.
  - Exports `SSH_AUTH_SOCK=~/.ssh/ssh_auth_sock` for the shell.
- Make sure `~/.ssh` exists with mode `700`.
- Configure tmux so new and existing panes use the stable path. For example, in `tmux.conf`:
  - `set -g update-environment "DISPLAY SSH_ASKPASS SSH_CONNECTION WINDOWID XAUTHORITY"` (i.e. remove `SSH_AUTH_SOCK` from the update list so tmux doesn't overwrite it with a stale path), and
  - `set-environment -g SSH_AUTH_SOCK ~/.ssh/ssh_auth_sock`.
- Keep the change idempotent and a no-op on the Mac and on non-SSH local sessions.

## Acceptance criteria

- [ ] From the Mac, `ssh <linux-host> 'ssh-add -l'` lists the Mac's keys.
- [ ] After login, `~/.ssh/ssh_auth_sock` exists on Linux and resolves to the current forwarded socket.
- [ ] Start tmux, detach, disconnect, reconnect, and reattach: `ssh-add -l` and `git fetch` over SSH work in the existing panes without manual env fixes.
- [ ] Multiple concurrent SSH logins don't break each other. Latest login wins, which is acceptable.
- [ ] No symlink loop is created when the shell is started from within tmux or when `SSH_AUTH_SOCK` already points at the stable path.
- [ ] Local (non-SSH) shells on both Mac and Linux are unaffected.
- [ ] `ForwardAgent` is not enabled for `Host *`.

## Out of scope

- Switching to `ProxyJump`, agent restrictions (`ssh-add -c`, `ssh-agent` confirm), or hardware keys.
- Handling agent forwarding for non-SSH remote tools (e.g. mosh) unless it already works with this approach.

## Risks / notes

- Agent forwarding exposes the Mac's keys to root on the remote host while connected. Only enable it for hosts I trust.
- If the old connection is still alive when a new one logs in, the symlink moves to the new socket and the old session loses agent access. This is acceptable for single-user use.
- Stale symlinks after the last disconnect are harmless, but the checks above should not treat a dead target as valid.

# Persist search page filters in localStorage

## Summary

Users lose their selected filters when they leave or reload the search page. Save the filter state to `localStorage` whenever it changes and restore it when the user returns, so they can pick up where they left off.

## Background

The search page keeps filter state only in memory (and possibly the URL; confirm during implementation). Navigating away, refreshing, or closing the tab resets all filters. Users who repeatedly apply the same filters have to re-enter them each visit.

## Goals

- Filters survive reload, navigation away and back, and browser restart.
- Persistence logic is reusable, implemented as a hook (e.g. `usePersistedState` / `usePersistedFilters`) rather than inline in the search page.
- Failures in storage never break the search page.

## Non-goals

- Syncing filters across devices or accounts (server-side persistence).
- Persisting non-filter state (search query text, sort, pagination), unless confirmed in open questions below.
- Migrating the other pages to the hook (the hook should make this possible later, but it's out of scope here).

## Requirements

### Behavior
1. On every filter change, write the full filter state to `localStorage` under a single namespaced, versioned key (e.g. `search.filters.v1`).
2. On search page mount, read the stored value, validate it, and initialize filters from it.
3. Writes should be debounced or batched if filters change rapidly (e.g. typing in a text filter), so we don't write on every keystroke.
4. Precedence: if the URL carries filter params, they win over stored values (see open questions).
5. A "Clear filters" action resets filters and removes the stored entry.

### Hook
- Signature along the lines of `usePersistedState(key, defaultValue, { version, validate })`, returning `[value, setValue, clear]`.
- SSR-safe: no `window`/`localStorage` access during server render; hydrate after mount without a hydration mismatch.
- Stored data is wrapped with a version so future schema changes can discard or migrate old values.

### Error handling
- Wrap all reads and writes in try/catch. Handle: storage unavailable (private mode, disabled cookies/storage), `QuotaExceededError`, `SecurityError`, malformed JSON, and values that fail validation or have a mismatched version.
- On any failure, fall back to default filters and keep the page fully functional with in-memory state. Do not show an error to the user.
- Corrupt or invalid stored data is discarded (removed) and defaults are used.
- Log failures at debug/warn level through the existing logging facility; don't throw.

### Analytics
Events to emit via the existing analytics layer (names are suggestions; match the project's convention):
- `search_filters_restored`: on successful restore. Properties: number of active filters, filter keys (not values, to avoid capturing user-entered text).
- `search_filters_persist_failed`: on read/write failure. Properties: error type (`quota`, `unavailable`, `parse`, `invalid`).
- `search_filters_cleared`: when the user clears filters.

Confirm that no PII is sent and that the events respect the existing consent settings.

### Compatibility
"Works everywhere" is interpreted as: the latest two versions of the browsers the project officially supports (Chrome, Firefox, Safari including iOS, Edge), plus private/incognito modes and storage-disabled configurations, which degrade gracefully to in-memory behavior. Also handle multiple tabs: a `storage` event listener is optional, and last-write-wins is acceptable by default.

## Testing

**Unit tests** (hook and filter serialization):
- Returns the default when nothing is stored.
- Restores a valid stored value.
- Writes on change (and respects debounce).
- Discards malformed JSON, invalid shape, and version mismatch.
- Does not throw when `localStorage` is undefined or `getItem`/`setItem` throw, including quota errors.
- `clear` removes the key and resets state.
- SSR render does not touch `localStorage`.

**E2E tests** (the project's existing e2e framework):
- Apply filters, reload, and the filters are still applied.
- Apply filters, navigate away and back, and the filters are restored.
- Clear filters, reload, and the defaults are shown.
- Pre-seed corrupt storage, and the page loads with defaults and no errors.
- Storage blocked (or throwing): the page works and filters function in-session.
- URL params take precedence over stored values (if confirmed).

## Acceptance criteria
- [ ] Filters persist across reload, navigation, and browser restart.
- [ ] Hook is reusable and has no search-specific logic.
- [ ] All storage failure modes fall back to defaults with no user-visible errors or uncaught exceptions.
- [ ] Analytics events fire as specified, with no filter values or PII.
- [ ] Unit and e2e tests listed above pass in CI.
- [ ] Docs are updated.
- [ ] Manually verified in the supported browsers, including private mode.

## Open questions
1. **URL vs. storage precedence:** Does the search page already sync filters to the URL? If so, should shared links override stored filters (assumed yes)?
2. **Scope of "all filters":** Does this include the search query text, sort order, and pagination? Assumed no: only filters.
3. **Expiry:** Should stored filters expire (e.g. after 30 days), or persist indefinitely?
4. **Privacy/consent:** Does storing filters in `localStorage` require a consent check under our cookie/storage policy?
5. **Supported browser list:** What's the official matrix for "everywhere"?
6. **Logged-in users:** Should the storage key be scoped per user to avoid leaking filters between accounts on a shared device?

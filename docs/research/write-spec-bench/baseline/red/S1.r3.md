# Persist search page filters in localStorage

## Summary
Users lose their filter selections when they leave or reload the search page. Save the filter state to `localStorage` whenever it changes and restore it when the user returns, so they can pick up where they left off.

## Background / Problem
Filters on the search page are not persisted, so navigating away, reloading, or closing the tab resets them. Users have to re-enter filters on every visit.

## Proposed Approach
- Add a reusable hook (working name `usePersistedFilters`) that wraps reading and writing filter state in `localStorage`. The hook should not be search-specific, so other pages can reuse it.
- Read the stored state once on mount and use it as the initial filter state.
- Write the full filter state to storage on every change. Debounce writes if filter changes can fire rapidly, such as text input or sliders.
- Use a single namespaced, versioned storage key (e.g. `search.filters.v1`) so the shape can change later without breaking old data.

## Requirements
1. **Save:** Any change to any search filter updates the stored value.
2. **Restore:** On returning to the search page, stored filters are applied before the first results request, so the page does not briefly fetch unfiltered results.
3. **Validation:** Stored data is validated against the current filter schema. Unknown, malformed, or outdated values are discarded, and the page falls back to defaults. Valid fields from partially valid data may be kept.
4. **Precedence:** If the URL already carries filter params, they override stored filters. *(Assumption, confirm below.)*
5. **Reset:** Clearing or resetting filters also clears the stored value.
6. **Error handling:** The page must work normally if `localStorage` is unavailable or throws (private mode, blocked storage, quota exceeded, corrupt JSON). Failures degrade to non-persistent behavior with no user-facing error. Log them for diagnostics.
7. **Compatibility:** Behavior is verified on the supported browser matrix (see open questions). If the page is server-rendered, the hook must not access `localStorage` during SSR and must avoid hydration mismatches.
8. **Analytics:** Emit events for restoring saved filters and for storage failures (see open questions for exact names and properties).
9. **Docs:** Document the hook (API, storage key and versioning, failure behavior) and note the persistence behavior in any user-facing or contributor docs for the search page.

## Testing
- **Unit tests (hook):**
  - Initial load with no stored value, a valid value, and a corrupt or invalid value
  - Write on change, including debounce behavior if applicable
  - Reset clears storage
  - `localStorage` missing, throwing on read, and throwing on write (quota)
  - Schema version mismatch
- **E2E tests:**
  - Set filters, reload, and confirm they are restored
  - Set filters, navigate away and back, and confirm they are restored
  - Reset filters, reload, and confirm defaults
  - URL params take precedence over stored filters
  - Page remains functional with storage disabled or blocked
- Run the e2e suite on each browser in the supported matrix.

## Acceptance Criteria
- [ ] Changing any filter persists it, and revisiting the page restores the same filters.
- [ ] The first results request after restore uses the restored filters.
- [ ] Invalid or corrupt stored data never breaks the page and falls back to defaults.
- [ ] The page works with `localStorage` unavailable or throwing.
- [ ] Reset removes the stored value.
- [ ] Unit and e2e tests above are added and passing in CI.
- [ ] Analytics events fire as specified and are verified in a test or dev environment.
- [ ] Hook and behavior are documented.

## Open Questions
1. **Which filters are persisted?** "All of the filters" is assumed to mean every user-controlled filter on the page. Should the search query text, sort order, and pagination be included or excluded?
2. **URL vs. storage precedence:** Should shared or bookmarked URLs always win over stored filters (assumed yes)?
3. **"Works everywhere":** Which browsers, devices, and rendering modes (SSR, embedded or webview) are in scope?
4. **Multi-tab behavior:** Should changes sync across open tabs (via the `storage` event), or is last-write-wins acceptable?
5. **Expiry and privacy:** Should stored filters expire? Does any filter contain user-identifying or sensitive data that shouldn't be stored, or that needs consent handling?
6. **Logged-in users:** Should filters be per-user (e.g. cleared on logout or shared devices) or per-browser?
7. **Analytics:** What are the event names and properties, and which analytics tool is used? Should the events include filter values or just counts and flags?
8. **Docs location:** Where do docs for this live (README, Storybook, internal wiki)?

## Out of Scope
- Server-side or account-level saved searches
- Persisting filters on pages other than search (the hook is reusable, but adoption elsewhere is a separate item)

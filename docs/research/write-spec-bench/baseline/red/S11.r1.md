# refactor(packages): make mise the primary package manager

## Summary

Make mise the primary package manager for runtimes, language-level global packages, and Homebrew-managed formulae. Version-switched CLIs move to mise tool backends (`[tools]`). Formulae that still need Homebrew artifacts move to mise's built-in `brew:` manager under `[bootstrap.packages]`. The existing Homebrew cask flow is retained.

## Motivation / Context

- Default Node, Python, and Ruby packages are managed separately from `mise-config.toml`.
- Homebrew owns a broader package set and bootstraps Ansible before mise is installed.
- Mise deprecates default Python package files: warnings are scheduled for 2026.11.0 and removal for 2027.11.0. Package behavior needs to move into TOML.
- Mise 2026.7.5 exposes `mise bootstrap packages`. Its built-in `brew:` manager installs Homebrew formulae into the canonical prefix without requiring Homebrew. `brew-cask:` exists but has narrower platform and lifecycle coverage.
- Making mise the orchestration boundary for residual Homebrew artifacts removes the need for separate Ansible Homebrew modules and Brewfile flows for formulae, and leaves one primary package manager going forward.

## Architecture / Ownership

- `mise-config.toml` is the single source of truth for runtimes, bootstrap tools, standalone CLIs, language packages, and shared Homebrew formula artifacts.
- Config conventions:
  - Canonical mise registry names for standalone CLIs.
  - Explicit `npm:` and `gem:` identifiers for ecosystem CLIs.
  - `pipx:` for isolated Python CLIs.
  - A Python tool-level `postinstall` for libraries that must be importable by the managed interpreter.
- Ansible orchestrates installation and cleanup. It does not duplicate the mise tool list in role variables.
- Mise's `brew:` manager owns formula artifacts that remain in the shared Homebrew prefix. These live in `[bootstrap.packages]` with `brew:` keys.
- The Homebrew CLI and Brewfile flow are responsible only for casks. Casks do not move to `brew-cask:` in this issue.
- Native OS package managers remain responsible for bootstrap prerequisites and system-level dependencies.

## Migration / Failure Handling

1. **Inventory.** List every formula in the core, Linux-specific, macOS-specific, and optional Homebrew declarations. Classify each as a version-switched `[tools]` candidate or a shared-prefix `[bootstrap.packages]` formula. Record the selected key and expected executable.
2. **Qualify.** For each `[tools]` candidate, install it and run its executable/version smoke check on both macOS and Linux. Only dual-platform successes move to `[tools]`. All others stay as `brew:` bootstrap packages.
3. **Greenfield bootstrap.** Install the verified standalone mise binary and expose the repository `mise-config.toml` at mise's global config location. On existing machines, verify that mise exposes `mise bootstrap packages` before applying config. If it does not, reinstall or update mise through the verified standalone path.
4. Run `mise bootstrap packages apply --yes`, then `mise install --yes`.
5. Run the initial playbook through `mise exec`, so the mise-provisioned Ansible is available without shell activation or Homebrew.
6. In Ansible, repeat package application and tool installation before smoke checks and before cleanup of migrated formulae.
7. Move core and platform formula declarations into the repository mise config. Move optional formula declarations into the mise optional-config example. Do not silently promote them into the core set. Leave only casks in the optional Brewfile.
8. **Cleanup.** After package application, tool installation, and smoke checks all succeed, use an already-installed Homebrew executable to converge the previously managed Homebrew copies of tools moved to `[tools]` to absent.
   - Do not install Homebrew solely for cleanup.
   - If any mise phase or smoke check fails, perform no cleanup and fail with package/tool context.
9. Surface targeted cleanup failures, including dependency-blocked removals, as actionable warnings without aborting unrelated provisioning.
10. Never run `mise bootstrap packages prune --manager brew`. It can remove formulae installed manually outside this repository. Limit automatic cleanup to the known formulae moving from Homebrew to `[tools]`.
11. In both greenfield bootstrap and Ansible convergence, keep package and tool phases explicit so package failures, tool failures, and smoke-check failures remain distinguishable.
12. Add the canonical Homebrew prefix directly to shell `PATH` when it exists. Do not depend on `brew shellenv`: mise-installed formulae create shared-prefix links rather than mise shims, and Linux may no longer have a Homebrew executable.
13. Install or invoke the real Homebrew CLI only for the retained macOS cask flow. Linux formula provisioning must not require Homebrew.

## Requirements

### Language packages
- Move default Node, Python, and Ruby gem package declarations into mise configuration.
- Use direct `npm:` and `gem:` tool entries for executable packages. Use `pipx:` only for Python CLI applications.
- Install `pynvim` through the Python tool-level `postinstall`, so `mise exec -- python -c "import pynvim"` succeeds.
- Delete the three legacy default-package files, and remove their symlink, doctor, and goss assertions once their entries are in mise config.

### Version policy
- Preserve floating channels: Node stays `lts`, Ruby stays on major `3`, and standalone CLI and language-package entries use `latest` unless a concrete compatibility constraint requires otherwise.
- Exact-version lock maintenance is out of scope.

### Formula migration
- Audit every repository-managed formula declaration: core, Linux-specific, macOS-specific, and optional examples.
- Move a portable CLI to `[tools]` only after tool installation and an executable/version smoke check succeed on both macOS and Linux. If qualification fails on either OS, keep it as a mise-managed `brew:` bootstrap package.
- Configure residual formulae in `[bootstrap.packages]` with explicit `brew:` keys, separate from `[tools]`.
- Keep macOS casks under Homebrew ownership. Do not add `brew-cask:` entries to `mise-config.toml`.
- Define mise as the primary package manager for future additions.

### Bootstrap
- Make greenfield bootstrap mise-first: install the standalone mise binary before Homebrew, provision Ansible through mise, and invoke the initial playbook through `mise exec` or an equivalently reliable non-interactive mise environment.
- Install Homebrew later in the Ansible role only when needed for the macOS cask flow.
- Use explicit phases everywhere: `mise bootstrap packages apply --yes`, then `mise install --yes`.
- Verify that the installed mise supports `mise bootstrap packages` before applying package declarations. Update it through the verified standalone path when needed.

### Cleanup safety
- On existing machines, remove only formulae whose replacements moved into `[tools]`, and only after those replacements install and pass smoke checks.
- Run targeted cleanup only when a real Homebrew executable already exists.
- Treat dependency-blocked removals as surfaced cleanup failures. Do not silently keep duplicate ownership, and do not abort unrelated provisioning.
- Preserve unrelated manually installed formulae.

### Platform and PATH
- Support Apple Silicon macOS and Linux x86_64/arm64. Mise's `brew:` manager does not support Intel macOS, so do not retain a parallel Intel Homebrew formula path.
- Ensure `/opt/homebrew/bin` (Apple Silicon macOS) and `/home/linuxbrew/.linuxbrew/bin` (Linux) are on `PATH` without `brew shellenv`.

### Mise package semantics to account for
- Package application is explicit.
- `latest` accepts an already-installed version.
- Upgrades use `mise bootstrap packages upgrade`.
- Formula pruning can remove packages installed by real Homebrew.

## Non-goals

- Removing Homebrew entirely.
- Moving macOS casks to mise.
- Replacing native OS package managers for bootstrap prerequisites or system-level packages.
- Introducing exact-version lock maintenance.
- Generating mise configuration from Ansible variables.
- Splitting core managed tools across repository-owned mise config fragments.
- Supporting Intel macOS through a separate Homebrew formula path.
- Treating the repository's mise config as authority to remove unrelated manually installed Homebrew formulae.

## Acceptance Criteria / Testing

- [ ] Each portable CLI migrated from a Homebrew formula installs through `[tools]`, and its executable/version command succeeds on both macOS and Linux.
- [ ] Every residual `brew:` bootstrap package applies and reports installed on its selected operating systems without a Homebrew executable.
- [ ] A greenfield bootstrap reaches and executes the Ansible playbook without Homebrew providing Ansible.
- [ ] Cleanup runs only after successful package application, tool installation, and smoke checks. It is idempotent, reports blocked removals, and never uses manager-wide prune.
- [ ] Canonical Homebrew prefix paths work without `brew shellenv`, and the Homebrew CLI is installed only for the macOS cask flow.
- [ ] `just upgrade` sends formula upgrades through mise, sends tool upgrades through mise, and leaves only cask upgrades to Homebrew.
- [ ] A full install run twice is idempotent across Ansible, mise, and Homebrew.
- [ ] Focused Bats coverage exists for:
  - the single-source package policy
  - exact `[tools]` vs `[bootstrap.packages]` ownership
  - OS selectors
  - cask-only Brewfile content
  - bootstrap ordering
  - targeted cleanup safety
  - upgrade separation
  - PATH behavior
  - removal of legacy package-file links
- [ ] Goss/integration assertions verify that representative runtime, standalone CLI, npm, pipx, and gem executables resolve through mise, and that `pynvim` imports from the mise-managed Python.
- [ ] Apple Silicon macOS and Linux CI paths exercise the qualified `[tools]` set, configured `brew:` package status, and smoke commands.
- [ ] The macOS CI job asserts the runner is arm64, so a runner-label architecture change fails explicitly.
- [ ] Linux integration coverage proves the mise `brew:` manager installs and exposes formulae without a Homebrew executable.
- [ ] `scripts/doctor.sh` checks and remediation text are updated:
  - `[tools]` failures point to `mise install`.
  - `brew:` package failures point to `mise bootstrap packages apply`.
  - No removed legacy symlink is expected.

## Decision log

- **Backend selection:** registry-first. Use canonical mise names for standalone CLIs, and explicit `npm:`, `pipx:`, and `gem:` entries for language packages.
- **Migration evidence:** a formula moves to `[tools]` only after install and smoke checks pass on both macOS and Linux. Otherwise it stays a `brew:` package.
- **Bootstrap:** mise-first end to end. Homebrew is installed later, only for the macOS cask flow.
- **Existing machines:** targeted automatic cleanup of migrated formulae, with blocked removals reported.
- **Versions:** floating channels preserved (Node `lts`, Ruby `3`, others `latest`).
- **Audit scope:** all formulae (core, platform-specific, optional). Casks stay in Homebrew.
- **Config architecture:** a single repository-managed `mise-config.toml`.
- **Cask scope:** formulae only. Casks stay in the Brewfile flow, not `brew-cask:`.
- **Architecture support:** Apple Silicon macOS only, with no Intel fallback.
- **Cleanup method:** targeted migration cleanup, not manager-wide `prune`.
- **Command boundary:** explicit phases (`mise bootstrap packages apply --yes`, then `mise install --yes`) in both bootstrap and Ansible, not the composite `mise bootstrap --yes`.

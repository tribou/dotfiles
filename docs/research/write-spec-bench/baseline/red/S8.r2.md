# Decide whether to adopt GitHub stacked PRs for work that exceeds the 65k-character limit

**Type:** Decision / spike
**Status:** Recommendation ready for review
**Owner:** artribou

## Summary

**Recommendation: No, not for this problem.** Stacked PRs and the 65k limit are different problems, and stacking does not fix the one that prompted the question. Handle oversized specs by splitting the *document*. Evaluate stacked PRs separately, as a way to review large *diffs*, on their own merits.

## Context

GitHub caps issue and PR bodies at 65,536 characters. Work that outgrows this ceiling hits one of two limits:

1. **Spec or description size:** the issue body can't hold the requirements, research, or plan.
2. **Change size:** the implementation is too large to review as one PR.

The question assumes stacked PRs address (1). They don't.

## Pressure test

| Claim | Assessment |
|---|---|
| Stacked PRs help when an issue exceeds 65k characters. | **Mostly false.** A stack divides *code changes* into dependent PRs. The issue body is untouched, and each PR still has its own 65k body limit. Stacking only helps indirectly, if the oversized issue is a symptom of oversized scope. |
| Large issues should become stacks. | **Partly true.** If the scope is genuinely large, stacking is a good way to review the code in layers. But the issue should be decomposed first, and the stack should follow that decomposition. |
| Adopting it is low-cost. | **Unverified.** It adds new tooling and workflow, and possibly a CLI or extension. It also changes merge, rebase, and CI behavior and needs team buy-in. |

### Risks of adopting stacking to solve the wrong problem

- The spec stays too large, and the team now has stack-management overhead on top.
- Review context fragments across PRs, while the source of truth stays crammed in one issue.
- Rebase and merge churn: a change at the bottom of a stack cascades upward. CI cost multiplies per layer.
- Preview-stage features can change or be limited by plan, org settings, or repo type. **I could not verify the current GA status, pricing, or limitations from this environment. Confirm before committing.**

### What actually solves the 65k problem

- **Parent issue with sub-issues:** keep a short parent (goal, scope, links) and put detail in child issues, each well under the limit.
- **Spec in the repo:** store long specs as markdown in `docs/`, and link to them from the issue. This gives versioning, review, and diffs.
- **Trim content:** move logs, transcripts, and research dumps to attachments or linked docs.
- **Split by deliverable:** an oversized issue is usually several issues.

### Where stacked PRs do fit

- A single feature whose diff is too big to review well, but that decomposes into ordered, individually reviewable layers (for example schema, then API, then UI).
- Teams already feeling pain from long-lived feature branches or from waiting on review before starting dependent work.

## Recommendation

1. **Do not** adopt stacked PRs as the answer to the 65k limit.
2. **Adopt** the parent/sub-issue plus in-repo spec pattern for oversized work. Set a soft guideline, such as splitting any issue body past about 40k characters.
3. **Run a small, time-boxed pilot** of stacked PRs on one real multi-layer change, judged on review latency, rebase pain, and CI cost. Revisit adoption only if the pilot shows a clear gain.

## Acceptance criteria

- [ ] Confirm current availability, limitations, and required tooling for GitHub stacked PRs in our org and plan.
- [ ] Document the "parent issue + sub-issues + in-repo spec" convention in the contributing guide, with a size threshold.
- [ ] Select one candidate change for a stacked-PR pilot, with a stated success measure.
- [ ] Record the pilot outcome and a go/no-go on broader adoption.

## Open questions

- What are the actual oversized issues: specs, research dumps, or generated content? The fix differs for each.
- Do our automation or agents write these issues? If so, they may need to enforce the size guideline.
- Does our branch protection, merge queue, or CI setup work well with dependent PRs?

## Out of scope

- Rewriting existing oversized issues.
- Changing review policy or merge strategy.

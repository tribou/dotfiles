# Decide whether to adopt GitHub stacked PRs for work that exceeds the 65k character limit

**Type:** Decision / spike
**Status:** Recommendation drafted, needs owner sign-off
**Recommendation:** **No-go as a fix for the character limit. Conditional pilot for large implementation diffs.**

## Question

Should we start using GitHub's stacked PRs for issues that grow past the ~65k character limit (GitHub's 65,536-character cap on issue, PR, and comment bodies)?

## Short answer

Stacked PRs and the character limit are different problems, and stacked PRs don't solve the one being asked about.

- The **65k limit** applies to *text*: issue bodies, PR descriptions, and comments.
- **Stacked PRs** split *code changes* into a chain of dependent PRs, each reviewed against the previous branch.

A stack of PRs does not make an oversized issue or spec fit. The limit follows the text, not the PR structure. Stacked PRs are still worth considering separately if the underlying work is also a large diff.

## Pressure test

| Claim | Assessment |
|---|---|
| "Stacked PRs let us work past the 65k limit." | **Mostly false.** Each PR in a stack has its own 65k body, so you could spread prose across PRs. But that scatters the spec across review artifacts, which is worse than one source of truth. |
| "The issue is too big, so the work should be stacked." | **Wrong direction.** An issue over 65k characters says the *spec* is too big or poorly structured. Fix that first. Stacking the implementation doesn't fix it. |
| "Stacking improves review of large changes." | **True, with caveats.** Small, ordered PRs review faster. The costs are rebase churn, merge-order coupling, CI cost per layer, and the risk that a mid-stack change invalidates the layers above. |
| "It's native now, so tooling risk is low." | **Unverified.** I could not confirm the feature's GA status, API and CLI coverage, or how it interacts with our branch protection, merge queue, and required checks. Treat these as open questions, not facts. |

## Why the 65k problem is better solved elsewhere

An issue that needs more than 65k characters usually has one of three causes:

1. **Multiple deliverables in one issue.** Split into a parent issue plus sub-issues, each with its own acceptance criteria.
2. **Reference material pasted inline** (logs, schemas, transcripts, research). Move it to a file in the repo, such as `docs/specs/<name>.md`, and link it from the issue.
3. **Accumulated discussion in the body.** Keep the body as the current-state spec and leave history in comments.

Each of these fixes is cheaper and more durable than adopting a new workflow. A spec in the repo is also versioned and reviewable through a normal PR.

## Options

1. **Adopt stacked PRs as the answer to oversized issues.** Rejected. It doesn't address the cause.
2. **Split by structure: parent issue, sub-issues, and long-form content in repo docs.** Recommended as the default for oversized issues.
3. **Use stacked PRs only when the implementation diff is large and naturally layered**, for example schema, then service, then UI. Recommended as a time-boxed pilot, independent of issue size.
4. **Do nothing.** Acceptable short term, but the limit will keep forcing truncation or ad hoc splitting.

## Recommendation

1. Adopt **Option 2** now as the standard for any issue approaching ~50k characters. This leaves headroom for edits.
2. Run **Option 3** as a pilot on one or two genuinely large, layered changes. Decide on wider adoption based on the results.
3. Do not make stacked PRs a policy response to the character limit.

## Work to do

- [ ] Confirm the current status of GitHub stacked PRs: GA or preview, availability on our plan, and CLI/API support.
- [ ] Check compatibility with our branch protection, required reviews, CODEOWNERS, merge queue, and CI triggers on non-default base branches.
- [ ] Write a short guideline: when to split an issue, when to move content to `docs/`, and the ~50k soft threshold.
- [ ] Pick one or two candidate changes for the stacked-PR pilot, with a maximum stack depth (suggest 3–4).
- [ ] After the pilot, record the findings: review latency, rebase pain, CI cost, and merge failures.

## Pilot success criteria

- Review turnaround per PR is measurably faster than comparable single large PRs.
- No more than one cascading rebase problem per stack.
- Merge order is handled without manual intervention, or the manual steps are documented and acceptable.
- Reviewers report that the stack is easier to follow than one large PR.

If these aren't met, drop the stacked-PR approach and keep Option 2.

## Open questions

- Does "issues that span past 65k" mean the **issue text** is too long, or the **resulting change** is too large? This item assumes the first and treats the second as the pilot. If it's only the second, Option 3 becomes the main path.
- Which tooling, if any, do we already use for stacking (for example Graphite or `git-branchless`)? That affects whether the native feature adds anything.
- Who owns the guideline and the pilot?

## Risks

- Adopting stacking on a preview feature could leave us dependent on behavior that changes.
- Splitting issues too aggressively fragments context. Keep one parent issue as the index.
